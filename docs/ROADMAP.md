## 0. How to execute this roadmap (read first, executing model)

### 0.1 Working rules
1. **One milestone per session, in order** (M1 → M9). Don't start a milestone until the previous one's acceptance criteria pass.
2. **Vertical slices.** Each milestone includes its backend, staff UI, patient UI, tests and seed data. Don't build "all backend first".
3. **Definition of Done** for every milestone: acceptance criteria pass; `make check` (lint + typecheck + tests) is green; Alembic migration included; `docs/PROGRESS.md` updated (what was built, deviations, open questions).
4. **Never invent medical or financial content.** Prices, fasting rules, preparation text, reference ranges, tube types and TATs come from seed files in `backend/seed/` whose header says `PLACEHOLDER — must be confirmed by BMU laboratory`. The software never produces clinical interpretation.
5. **Every status change goes through a transition function** (Section 7.3), never `obj.status = ...` directly.
6. **Decisions not covered here:** choose the simplest option consistent with Section 3. Record it as an ADR in `docs/adr/NNNN-title.md` (context, decision, consequences, ≤ 1 page).
7. Items tagged **[BMU]** are institutional/human tasks. Don't block code on them: build behind a config flag or adapter with a mock, and list the open item in `docs/PROGRESS.md`.
8. Secrets live only in `.env` (never committed). `.env.example` lists every key.

### 0.2 `CLAUDE.md` to create at the repo root

## 1. Context

At BMU (PG Hospital), a patient doing a lab test currently stands in **four physical queues**:

```
Prescription → Q1 counter (tests written on a multi-copy slip) → Q2 bank booth (pay, bank stamps)
→ Q3 sample collection (code written on tube) → wait ~1 day → Q4 report counter
```

The institution already links everything with **one code written on the patient copy, the bank copy, the hospital copy and the test tube**. That practice works and staff know it, so we keep it and make it digital:

- The code is **generated by the system, carries a check digit, and is printed as a barcode/QR** on all copies and tube labels, instead of being handwritten.
- Registration, verification, payment and report delivery can happen **online** (a PWA, with SMS), so an online patient comes to the hospital **once**, in a booked arrival window, only to give the sample.
- Patients without smartphones use the **same system through a help desk**, and still get paper copies. They also skip queues: payment confirmation reaches the collection queue instantly, so they don't go back to the counter.

The target is a pilot-ready system for BMU, with real payment gateways (bKash, Nagad, Upay, Rocket and cards) and a bank teller portal.

## 2. Where this plan differs from the earlier discussion (and why)

| # | Earlier idea | This plan | Why |
|---|---|---|---|
| 1 | OCR reads the prescription and suggests tests (V1) | **V1 has no OCR.** The patient photographs the prescription and picks tests from a searchable catalog (with aliases such as "S. Creat" → Creatinine), and staff verify against the photo. OCR arrives post-pilot, as suggestions only. | A human verifies anyway. OCR of handwritten Bangladeshi prescriptions is unreliable, and leaving it out removes risk and scope from the MVP. |
| 2 | Pay first, then book a slot | **Pick a slot → 15-minute hold → pay → booking confirmed.** | Otherwise a patient can pay and then find no slot. |
| 3 | One report per order | **A report per department section, released independently**, with order items tracked one by one | CBC is ready the same day while a culture takes 3 days. The patient shouldn't wait for the slowest test. |
| 4 | "Code" was implicit | **Universal Order Code** with a Damm check digit on the slip copies, tube labels, SMS and report (Section 4) | Matches BMU's current paper practice and catches typing errors by tellers and staff. |
| 5 | "Payment reaches the bank automatically" | A **gateway aggregator** (SSLCommerz covers bKash/Nagad/Upay/Rocket/cards) settles into BMU's merchant account. A **bank teller portal** handles in-person bank payment, plus a daily **statement import** for reconciliation. | Doesn't depend on a bank API integration the bank may never provide. |
| 6 | Lab enters every result in the new system | A per-department **result mode: `STRUCTURED` or `PDF_UPLOAD`**. `PDF_UPLOAD` attaches the existing analyzer/LIS printout, which a pathologist then approves. | The pilot doesn't force the lab to re-type results. Structured entry and analyzer integration come later. |
| 7 | Prescription verification queue | Verification has an **SLA and escalation**. For walk-ins, help desk staff verify **inline** while the patient stands there. | Otherwise the verification queue becomes the new bottleneck. |
| 8 | Native Android app | **PWA only.** Android later via a Trusted Web Activity wrapper, reusing the same code. | No install friction and one codebase. |
| 9 | Nothing about outages | A **downtime procedure** with pre-printed code sticker sheets from reserved code ranges, which staff back-enter later | A hospital can't stop when the server goes down. |
| 10 | Paper removed for online users | **Paper is configurable**: `REQUIRE_PAPER_HOSPITAL_COPY` lets the lab keep a printed hospital copy during the transition. | Adapts to the current way of working, and can be switched off later. |

## 3. Product principles (non-negotiable)

1. **One backend, every channel.** APP, WEB, HELPDESK, WALKIN and (later) KIOSK all create the same `Patient → LabOrder → Payment → Appointment/Token → Specimen → Result → Report` records. `channel` is only a field.
2. **One code everywhere.** The Universal Order Code identifies the order on every paper, screen, SMS, tube and report.
3. **Never ask twice.** Once the system knows something (prescription, payment, identity), no counter asks for it again.
4. **Paper is a first-class output.** Every digital artefact has a printable form: slip, token, label, report.
5. **Humans authorise medical decisions.** Staff verify orders and a pathologist releases reports. The software never interprets results.
6. **Every state change is validated, timestamped and audited** (Section 7.3). Timestamps give the KPIs for free.
7. **Measure, don't promise.** No "20-minute visit" claims until the baseline and pilot data exist (Section 13).

## 4. The Universal Order Code: one code on the bank, hospital and patient copies and the tube

### 4.1 Format
```
YYMMDD-NNNNN-C        e.g.  260924-00182-7
│      │     └ Damm check digit over the 11 digits (catches every single-digit typo and adjacent swap)
│      └ daily serial, 00001–89999 (90000–99999 reserved for downtime blocks, see 4.4)
└ date the code was issued (Asia/Dhaka) = submission date for normal orders
```
- Numeric only, so it is easy to read aloud, type on a phone, enter at the bank, and fits the dense **Code128-C** barcode.
- Stored canonically as 12 digits (`260924001827`) and displayed with dashes. The input parser accepts either form, strips spaces and dashes, and **rejects bad check digits** with the message "code mistyped".
- The serial comes from an atomic `daily_counter` row (`UPDATE … SET value = value + 1 … RETURNING value`). Gaps are acceptable and documented.
- The code is assigned when an order is **submitted** (not while it is a draft), so drafts don't use up codes.
- Implement in `backend/app/core/codes.py`: `damm_check(digits) -> int`, `generate_order_code(session, date)`, `parse_order_code(text) -> str | raises`, `tube_accession(order_code, n) -> str`. Test vector: the Damm check digit of `572` is `4`.

### 4.2 Where the code appears

| Place | What's printed | Barcode/QR content |
|---|---|---|
| **Patient copy** (slip, part 1) | Code (large), patient name/age/sex, tests, amount, payment status, arrival window or token, preparation instructions, "get your report online / SMS" instructions | QR = code only (no personal data) |
| **Bank copy** (slip, part 2) | Code, patient name, amount in figures and words (Bangla + English), account head, teller stamp/signature box | Code128 = code |
| **Hospital copy** (slip, part 3) | Code, patient, tests, prescription reference, verifying staff, fee category/waiver approver | Code128 = code |
| **Tube label** (50×25 mm thermal) | `260924-00182-7 · T01`, patient name, age/sex, container type/colour, test abbreviations, collection date/time | Code128-C = `26092400182701` (code + 2-digit tube number) |
| **Queue token** (80 mm thermal) | Token `W-042`, code, current serving number | QR = code |
| **SMS** | Code, amount/status, window/token, report link | — |
| **Report PDF** | Code, tube accession(s), report number, verification QR | QR = verification URL (Section 7.2) |

Slip layout: **one A4 page cut into three parts along dashed lines**, each part headed **PATIENT COPY / BANK COPY / HOSPITAL COPY** (Bangla + English).
- If the order is **already paid online**, the bank copy prints "PAID ONLINE — Txn <id>" or is omitted (config `PRINT_BANK_COPY_WHEN_PAID=false`).
- An online patient doesn't need to print anything. The app/SMS QR is enough, unless `REQUIRE_PAPER_HOSPITAL_COPY=true`, in which case the collection station prints the hospital copy on check-in.

> **[BMU] confirm:** the analyzers' maximum barcode length (some accept only 10–13 characters) and the label printer model. Tube accession length is configurable (`TUBE_ACCESSION_FORMAT`).

### 4.3 Tube grouping
Tests are grouped into tubes by `(container_type, department)` by default (config `TUBE_GROUPING = container | container_department`). Example: CBC plus HbA1c → one EDTA tube; Creatinine plus lipid profile → one plain/SST tube. So an order with 4 tests might print 2 labels.

### 4.4 Downtime code blocks
An admin generates **downtime sticker sheets** in advance. They use the normal 12-digit format, with the date part = the **block issue date** and serials from the reserved 90000–99999 range (for example `260901-90001-C`), allocated per counter as a `DowntimeCodeBlock`. So the parser, check digit, barcodes and analyzers all work unchanged; the order's real date lives in `submitted_at`. Each code prints ×6 identical barcode stickers (3 slip copies + up to 3 tubes). During an outage, staff use paper slips with the stickers, exactly like today. After recovery, the "Back-entry" screen creates orders with the pre-assigned code (the system accepts only unused codes from issued blocks).

## 5. End-to-end journeys (the acceptance tests follow these)

### 5.1 Online patient (smartphone)
1. PWA → language (বাংলা default / English) → mobile number → OTP.
2. Home: **Book a Test · My Appointments · My Reports** (nothing else).
3. "Who is this for?" → self or a family member (add name, sex, date of birth *or* age, relation).
4. Photograph the prescription (1–3 images) and search/select tests. Submit → gets a **code** → status "Waiting for verification (usually within N hours)".
5. Staff verify (confirm, edit tests, or request clarification) → SMS "Tests verified, pay ৳X".
6. Review tests, prices and preparation → pick a date and a **15-minute arrival window** (morning only if any test needs fasting) → the slot is **held for 15 minutes**.
7. Pay: bKash / Nagad / Upay / Rocket / card through the gateway, **or** "Pay at hospital".
8. Confirmation screen and SMS: code, QR, arrival window, preparation. Reminder SMS the evening before.
9. Arrive → go straight to the **Online/Appointment** lane → scan QR at check-in → token `A-0xx` → called to a station → labels printed, sample taken → SMS "Sample collected. Report expected by …".
10. Each section's report is released → SMS with link → view/download the PDF, share a time-limited link with the doctor, or collect a printout at the counter.

### 5.2 Walk-in, no smartphone, pays at the bank booth (today's paper flow, digitised)
1. Help desk: search the patient by mobile (to avoid duplicates) or register them. Staff look at the paper prescription, select the tests, and **verify inline**.
2. **Print the 3-part slip** (code + barcodes). The patient's mobile gets an SMS with the code (if they have a phone).
3. Bank booth: the teller **scans the bank copy barcode** (or types the code) → sees name and amount → "Receive ৳X" → stamps the copy → the system marks the order **PAID** and **issues a collection token `W-0xx` immediately** (the teller prints it on an 80 mm printer, and it's also sent by SMS).
4. The patient goes **directly to sample collection** without returning to the counter. The queue display shows the token.
5. Collection: scan the patient copy or token → labels → sample.
6. Report: the SMS says it's ready → the counter scans the patient copy → identity check (name plus the last 4 digits of the mobile, or the patient copy itself) → print → marked collected.

### 5.3 Verified online, "Pay at hospital"
The order stays `AWAITING_PAYMENT`. The SMS carries the code, and the bank teller or cashier can look it up **by code without any paper**. Once paid, a `W` token is issued. (Slot booking needs online payment in V1. Config `ALLOW_UNPAID_BOOKING_PCT` defaults to 0.)

### 5.4 Emergency / free / poor fund / staff concession
Help desk sets `fee_category`. A user with `waiver.approve` approves it (with a reason), which creates a `WAIVER` payment record. Emergency orders get priority tokens `P-0xx`, called before others. All of this is audited.

### 5.5 Sample rejected (haemolysed, insufficient, clotted, mislabelled)
Lab reception rejects the tube with a reason → the affected items move to `RECOLLECT_REQUIRED` → SMS to the patient → free rebooking (a new window, or priority walk-in). The same order code is kept, and the new tube gets the next tube number.

### 5.6 Report correction
The pathologist amends a released report → **new version v2** with a mandatory reason. v1 is marked `SUPERSEDED` (never deleted), the verification page shows "superseded by v2", and the patient gets an SMS.

### 5.7 Downtime
Section 4.4, plus the runbook `docs/runbooks/downtime.md`.

## 6. Architecture

### 6.1 Stack (keep it boring)
- **Backend:** Python 3.12, FastAPI, SQLAlchemy 2.0 (sync sessions; simpler and enough at this load), Alembic, Pydantic v2, `uv` for dependencies.
- **DB:** PostgreSQL 16. **Cache/broker:** Redis 7. **Jobs:** Celery + Celery Beat (SMS, PDFs, payment re-query, reminders, expiry, nightly reconciliation).
- **Files:** MinIO (S3-compatible, on-prem), with private buckets and short-lived (5 min) presigned URLs.
- **PDF:** **WeasyPrint** (HTML/CSS → PDF). It shapes Bengali script correctly through Pango/HarfBuzz; ReportLab does **not**, so don't use it. Fonts: Noto Sans Bengali + Noto Sans, bundled in the image.
- **Barcodes/QR:** `python-barcode` (Code128, SVG) and `segno` (QR, SVG), embedded in the HTML templates.
- **Frontend:** pnpm workspace; React 18, TypeScript (strict), Vite, React Router, TanStack Query, react-hook-form + zod, Tailwind + shadcn/ui, react-i18next, `vite-plugin-pwa`; API client generated from FastAPI's OpenAPI (`openapi-typescript` + `openapi-fetch`).
- **Scanning:** USB barcode scanners act as keyboards, so the staff app has a global `useScanner()` hook that detects fast keystroke bursts ending in Enter. Camera scanning uses `@zxing/browser` as a fallback.
- **Printing:** the browser prints server-generated PDFs sized per printer (A4 slip, 80 mm token, 50×25 mm label). Counter PCs run Chrome with `--kiosk-printing` for one-click silent printing. (ZPL direct printing is a post-pilot option.)
- **Infra:** Docker Compose (api, worker, beat, postgres, redis, minio, nginx), Ubuntu LTS on-prem or a Bangladeshi data centre, TLS through nginx. GitHub Actions CI runs lint, typecheck, tests and image builds.
- **Architecture style:** a **modular monolith**. Modules talk through service functions, never through each other's tables.

### 6.3 API zones
- `/api/v1/patient/*`: patient JWT (from OTP). A patient only ever sees patients under their own account.
- `/api/v1/staff/*`: staff JWT plus a permission check per endpoint (`require("order.verify")`).
- `/api/v1/public/*`: report verification, payment gateway IPN/callbacks, and the queue display feed (display device token).
- Errors: `{code, message_key, params}`, which the frontend translates.
- Pagination is cursor-based. Order lookups also accept the code in any format (`parse_order_code`).

### 6.4 Auth
- **Patient:** OTP (6 digits, stored hashed, 5-minute TTL, max 5 attempts; rate limit of 3 sends per 15 minutes per mobile, plus per IP). Access JWT for 15 minutes; refresh token in an httpOnly cookie for 30 days, rotated and revocable.
- **Staff:** username + password (argon2), **TOTP required** for PATHOLOGIST/ADMIN/SUPER_ADMIN/WAIVER approvers. 12-hour session, 30-minute idle lock (re-enter PIN), lockout after 5 failures. Each staff session records the station/counter.
- **Display devices:** long-lived device token, created by an admin, allowed only the display feed.

## 7. Domain model

### 7.1 Entities (key fields only; every table has `id` UUID, `created_at`, `updated_at`)
- **Account**: mobile (unique, E.164), preferred_language, status.
- **Patient**: account_id (nullable for help-desk-only patients), hospital_patient_no (optional BMU registration number), full_name, full_name_bn, sex, date_of_birth *or* (age_years + age_estimated=true), mobile, nid (optional, encrypted), relation_to_account, created_channel.
- **Staff**: username, full_name, designation, password_hash, totp_secret (encrypted), is_active; **StaffRole** (staff_id, role, department_id nullable for department-scoped roles).
- **Department**: code, name_en/bn, result_mode (`STRUCTURED` | `PDF_UPLOAD`), report_signatory_staff_ids.
- **LabTest**: code, name_en/bn, aliases[] (used for search), department_id, specimen_type (BLOOD/URINE/STOOL/SWAB/OTHER), container_type (EDTA/PLAIN/SST/FLUORIDE/CITRATE/URINE_CUP/…), collection_resource (BLOOD_COLLECTION/URINE/SPECIAL), fasting_required, fasting_hours, prep_en/bn, tat_hours, requires_prescription, active.
- **LabTestPrice**: test_id, amount (integer paisa), fee_category, effective_from/to. The order item **snapshots** the price.
- **TestParameter** (for STRUCTURED results): test_id, name, unit, decimals, sort, **ReferenceRange** rows (sex, age_min/max in days, low, high, text), critical_low/high.
- **Prescription**: patient_id, images[] (object keys), doctor_name, prescription_date, status, verified_by/at, clarification_note, sla_due_at.
- **LabOrder**: **order_code** (unique), patient_id, prescription_id, channel, status, priority (NORMAL/ELDERLY/DISABLED/EMERGENCY), fee_category (GENERAL/FREE/POOR_FUND/STAFF/CONCESSION), waiver_approved_by, subtotal/discount/total (paisa), submitted_at, created_by_staff_id.
- **LabOrderItem**: order_id, test_id, price_snapshot, status, specimen_id, department_id.
- **Payment**: order_id, method (GATEWAY/BANK_TELLER/COUNTER_CASH/WAIVER), provider (SSLCOMMERZ/BKASH/NAGAD/…/null), amount, status, gateway_tran_id (our id sent to the gateway), provider_txn_id, bank_receipt_no, received_by_staff_id, paid_at, reconciliation_status. **PaymentEvent** (append-only raw callbacks/validations). **Refund**. **BankStatementImport / BankStatementLine** (matched_payment_id, match_status).
- **CapacityTemplate**: resource, weekday, start/end, window_minutes, capacity_per_window, walkin_reserved_pct. **CapacityOverride**: date, closed/holiday, custom capacity. **Slot**: resource, date, window_start/end, capacity, booked (materialised 14 days ahead by a nightly job; `CHECK booked <= capacity`).
- **Appointment**: order_id, slot_id, status, hold_expires_at, reschedule_count.
- **QueueToken**: date, queue (A = appointment, W = walk-in, P = priority), number, order_id, status, called_at, station_no, served_at.
- **Specimen**: accession (`code + NN`), order_id, container_type, status, collected_by/at, received_by/at, rejection_reason, recollection_of_id.
- **Result**: order_item_id, parameter_id, value_num/value_text, unit_snapshot, ref_range_snapshot, flag (N/L/H/LL/HH/A), entered_by/at. **ResultAttachment** (PDF_UPLOAD mode).
- **Report**: report_no, order_id, department_id; **ReportVersion**: version, status, pdf_key, sha256, released_by/at, amendment_reason, verify_token (random 128-bit, URL-safe). **ShareLink**: token, expires_at, revoked. **ReportDelivery**: printed_by/at, collected_by_name.
- **Notification** (outbox): channel, template_key, lang, to, params, status, attempts, provider_msg_id.
- **AuditLog** (append-only; a DB trigger blocks UPDATE/DELETE): actor_type/id, action, entity_type/id, patient_id, before/after JSON, ip, user_agent, at.
- **DailyCounter**, **OtpChallenge**, **DowntimeCodeBlock**, **Setting** (runtime config such as SLA hours and paper flags).

### 7.2 Report verification
The QR on the report points to `https://<host>/verify/<verify_token>`. The page shows only: report number, **masked** name (`Ab*** Ka***`), age/sex, test names, release date/time, version, status (VALID / SUPERSEDED / REVOKED) and the SHA-256 of the PDF. It never shows result values. A cryptographic PAdES PDF signature is post-pilot (M10).

### 7.3 State machines
Implement a generic `core/state_machine.py`: `transition(entity, to, actor, reason=None)` checks an allowed-transitions map, sets status plus a `<status>_at` timestamp, writes an AuditLog row and a domain event (used for SMS and KPIs), and raises `InvalidTransition` otherwise.

**LabOrder**
```
DRAFT → PENDING_VERIFICATION → (NEEDS_CLARIFICATION ↔ PENDING_VERIFICATION) → AWAITING_PAYMENT → PAID
      → READY_FOR_COLLECTION (has appointment or token) → CHECKED_IN → COLLECTED → IN_LAB → COMPLETED
Side exits: REJECTED (from verification), EXPIRED (unpaid after N days), CANCELLED (before collection),
            REFUND_PENDING → REFUNDED
Help-desk orders go straight to AWAITING_PAYMENT (inline verification). WAIVER → PAID immediately.
COMPLETED is set automatically when every item is RELEASED or CANCELLED.
Patient-facing progress label is derived (e.g. "2 of 3 reports ready").
```
**LabOrderItem:** `ORDERED → COLLECTED → RECEIVED → RESULT_ENTERED → VERIFIED → RELEASED`, plus `RECOLLECT_REQUIRED → COLLECTED` and `CANCELLED`.
**Payment:** `INITIATED → PENDING → SUCCESS | FAILED | CANCELLED | EXPIRED`; `SUCCESS → REFUND_PENDING → REFUNDED`.
**Appointment:** `HELD (15 min) → BOOKED → CHECKED_IN → COMPLETED`; `HELD → RELEASED`; `BOOKED → NO_SHOW | CANCELLED | RESCHEDULED`.
**Specimen:** `LABELLED → COLLECTED → RECEIVED | REJECTED`.
**ReportVersion:** `DRAFT → PENDING_VERIFICATION → RELEASED → SUPERSEDED | REVOKED`.

### 7.4 Concurrency rules (must be tested)
- **Slot booking:** `UPDATE slot SET booked = booked + 1 WHERE id = :id AND booked < capacity RETURNING id`. If no row comes back, the slot is full. An expired hold decrements in a Beat job every minute.
- **Payment success is idempotent:** there is a unique `(provider, provider_txn_id)` and a row lock on the payment. A second IPN or teller click causes no double effect, and the teller UI shows a large "ALREADY PAID".
- **Order code and token serials:** atomic counters (4.1).

## 8. Roles and permissions
Permissions are strings (`order.verify`, `payment.teller.receive`, `report.release`, …) mapped to roles in code (`identity/permissions.py`). Department-scoped roles only see their department's worklists.

| Role | Main screens |
|---|---|
| HELP_DESK | Patient search/registration, walk-in orders with inline verification, slip printing, reprints |
| VERIFIER | Prescription verification queue (online orders), SLA view |
| BANK_TELLER | **Teller screen only**: scan/type code → receive → print token; own day-close summary |
| CASHIER | Counter cash / counter bKash-QR receipt (if BMU allows a hospital counter) |
| COLLECTOR | Check-in, call next, collection station, label printing, tube scan confirmation |
| LAB_RECEPTION | Receive tubes by scan, reject with reason |
| TECHNICIAN (dept) | Worklist, result entry / PDF upload |
| PATHOLOGIST (dept) | Verify and release, batch-release normals, amend (new version) |

## 9. Integrations (all behind adapters with a `mock` implementation used in dev/tests)

- **PaymentProvider interface:** `initiate(payment) -> redirect_url`, `validate(callback_payload) -> ValidationResult`, `query(payment) -> status`, `refund(payment, amount)`.
  - **SSLCommerz (pilot primary):** one integration covering bKash, Nagad, Upay, Rocket, cards and internet banking. Flow: create session → redirect → **IPN to `/public/payments/sslcommerz/ipn`** → call the **Validation API** with `val_id` → check `tran_id`, amount and currency match → SUCCESS. **Never trust the browser success redirect.** A Beat job re-queries payments stuck in PENDING for more than 10 minutes.
  - **bKash Tokenized Checkout direct** (optional adapter, M10) if BMU wants lower fees. The same interface later serves Nagad/Upay direct.
  - **Teller / Counter / Waiver:** internal providers (no external call).
  - **[BMU]** BMU needs a merchant account in its own name, with settlement to its bank account. Callbacks need a **publicly reachable HTTPS endpoint** even when the server is on-prem.
- **Reconciliation:** a nightly job matches (a) gateway settlement reports and (b) uploaded bank statement CSVs (column mapping configurable per bank) against payments. Any mismatch goes to the "Reconciliation exceptions" screen.
- **SMS:** a `SmsProvider` interface with a Bangladeshi bulk SMS provider adapter (e.g. SSL Wireless / a BTRC-registered masking provider), plus mock. Unicode Bangla SMS allows 70 characters per segment, so templates stay within 2 segments. Sending goes through the outbox table and a Celery retry with backoff. Templates live in `notifications/templates/{bn,en}.yaml`.
- **Storage:** an S3 client to MinIO. Buckets: `prescriptions`, `reports`, `attachments`.
- **Web push** (optional, M10). SMS stays the guaranteed channel.

### M2 — Catalog, patients, patient login

### M3 — Prescriptions, orders, the 3-part slip
- Prescription upload (client-side image compression to ≤ 1 MB, 1–3 images), a test picker, and submit, which creates the order with its **code** (`PENDING_VERIFICATION`).
- Verification queue: the image viewer (zoom/rotate) next to the selected tests; confirm / edit tests / request clarification / reject; SLA countdown and overdue highlight; SMS on each outcome.
- Help desk walk-in order: register or find the patient → select tests while viewing the paper prescription (optional webcam photo) → inline verification → `AWAITING_PAYMENT`.

- `documents/`: **3-part slip PDF** (4.2) in Bangla and English, with barcode and QR, and reprint (every reprint is audited and watermarked "REPRINT n").

- **Acceptance:** E2E online patient: submit → staff verify → patient sees the price and prep text. E2E help desk: walk-in → slip PDF has three parts, each with the same code, and the barcode decodes to it (test with `pyzbar` or `zxing` in CI). Price is snapshotted: a later price change doesn't alter existing orders.

### M4 — Payments (gateway, bank teller, counter, reconciliation)
- The payment service and state machine, the adapter interface, and the `mock` provider (with a fake gateway page for dev/E2E).
- SSLCommerz adapter (sandbox): initiate, IPN, validation, query job, refund.
- **Bank teller screen:** a large scan field → shows name, code and **amount** → "Received" (asks for the bank receipt number if configured) → PAID → prints the token (80 mm) and sends it by SMS. It shows "ALREADY PAID" / "NOT VERIFIED YET" / "EXPIRED" states clearly. Tellers get a day-close summary (count and total per teller) to print.
- Counter cash (if enabled), refunds (who can approve, reason, provider refund call or manual refund record), unpaid order expiry job.
- Reconciliation: statement CSV upload with column mapping, auto-matching by code and amount, and an exceptions screen.
- PWA: payment method choice (bKash / Nagad / Upay / Rocket / card logos, all through the gateway, plus "Pay at hospital"), and the result pages (success / failed / pending, which polls status).
- **Acceptance:** duplicate IPN → one SUCCESS and one audit trail (tested). An IPN with the wrong amount → payment flagged `FAILED` with reason `AMOUNT_MISMATCH` (tested). Two tellers receiving the same code at once → exactly one success (tested). Teller day-close totals equal the sum of their payments. SSLCommerz sandbox round-trip documented in `docs/runbooks/payments.md`.

### M5 — Scheduling, check-in, queue
- Capacity templates and overrides/holidays (admin UI), the nightly slot materialiser, the fasting → morning-only rule, and the walk-in reserved percentage.
- Slot picker (PWA) → **15-minute hold** → payment → BOOKED. Hold expiry job. Reschedule (max N times, not within X hours of the slot), cancellation, and the refund policy hook.
- Reminder SMS the evening before; the no-show job at the end of the day.
- Queue: tokens A/W/P. **Check-in kiosk-mode page** at the collection entrance (scan QR → token printed). If they arrive outside their window, it offers the walk-in queue. Station "Call next" with the rule: P first, then A and W interleaved at a configurable ratio (default 2:1). **Display screen** `/display/:queueId` (large font, bn/en, voice announcement via the Web Speech API optional, SSE feed).
- **Acceptance:** a concurrency test with 50 parallel bookings on a slot of capacity 4 → exactly 4 succeed. An expired hold frees the slot. Fasting orders can't pick afternoon windows. The display updates within 2 s of "Call next".

### M6 — Sample collection and specimen tracking
- Collection station: scan token/QR/slip → order card (tests, payment ✓, verification ✓, prep reminder such as "Fasting? yes/no" question) → **tube plan** (4.3) → print labels (50×25 mm PDF) → **scan each printed label to confirm** it belongs to this order (a mismatch shows a red block) → mark collected. If `REQUIRE_PAPER_HOSPITAL_COPY`, the hospital copy prints now.
- Lab reception: scan tubes on arrival → RECEIVED; reject with reason → the recollection flow (5.5).
- SMS: "Sample collected, report expected by <max TAT>".
- **Acceptance:** E2E: a paid online order checks in, gets labels, is collected and received. Scanning another order's tube at confirmation is blocked. A rejection triggers a recollection SMS and a free rebooking, with the tube number incremented.

### M7 — Results and verification
- Department worklists (received specimens, age, priority first).
- `PDF_UPLOAD` mode: attach the analyzer/LIS printout per item or section.
- `STRUCTURED` mode: an entry grid from TestParameters, auto flags against sex/age reference ranges, critical values highlighted with a mandatory "critical value communicated to/at" field.
- Pathologist verification: side-by-side view, release individually or batch-release (normals only), send back to the technician with a comment.
- **Acceptance:** results can't be released by the person who entered them (configurable, default on). Flags are computed correctly for boundary values (tested). A section is released independently of the other sections in the same order.

### M8 — Reports and delivery
- Report PDF generation (WeasyPrint): institution header, patient, code, accession(s), sample/report times, results with units and reference ranges and flags (or the embedded uploaded PDF pages), signatory, verification QR, and a page footer "Report no. / version / page x of y". Store the SHA-256.
- Versioning and amendments (5.6), and the public verification page (7.2).
- PWA: My Reports (grouped by order), view/download (presigned URL), **share link** (7-day expiry, revocable), "request printed copy".
- Report desk: find by code / mobile / scan → identity check → print → mark collected (with the collector's name if it isn't the patient).
- SMS "Report ready" with a short link.
- **Acceptance:** a Bangla name renders correctly in the PDF (visual snapshot test). The verification page shows no result values. An amended report shows v2, v1 shows SUPERSEDED, and both remain downloadable by staff. An expired or revoked share link returns 410. Every staff report view is written to the audit log.

### M9 — Operations hardening → **PILOT GO-LIVE**

## 11. Cross-cutting requirements
- **Security:** HTTPS only; private object storage with presigned URLs; NID/TOTP secrets encrypted with app-level encryption (key from env); PII masked in logs; every staff read of a patient's report/result is audited; least-privilege roles; CSRF protection on cookie refresh; CSP. Data stays in Bangladesh **[BMU confirm hosting + legal: applicable Bangladeshi data protection rules]**.
- **i18n:** Bangla is the default for patients, English for staff (both switchable). Numerals follow the language (৳১,২৫০ vs ৳1,250). Dates use `Asia/Dhaka`.
- **Accessibility/low-end devices:** large tap targets, readable at 360 px width, initial PWA bundle < 300 KB gzipped, works on slow 3G, offline shell showing the last confirmation QR from cache.
- **Money:** integer paisa everywhere, never floats.
- **Time:** stored in UTC, displayed in Asia/Dhaka. Business "day" boundaries use Dhaka time.

## 12. Testing strategy and end-to-end verification
- **Unit:** codes, state machines, tube grouping, capacity/slot maths, reference-range flagging, SMS template length.
- **API tests:** real Postgres (docker) with per-test transactions. Concurrency tests (slots, payments, counters) run real parallel sessions.
- **E2E (Playwright, `make e2e`) golden paths:**
  1. Online: OTP → prescription → verify (staff) → slot hold → mock gateway pay → check-in → labels → collect → receive → PDF upload → release → patient downloads the report → verification page is VALID.
  2. Walk-in: help desk order → 3-part slip → teller receives → token → display → collect → structured results → release → report desk prints.
  3. Rejection → recollection. 4. Amendment → v2. 5. Downtime back-entry.
- `make seed` creates a demo dataset (placeholder catalog, staff for every role with printed demo credentials, capacity for the next 14 days) so anyone can click through.

## 15. Key risks and mitigations
| Risk | Mitigation |
|---|---|
| The verification queue becomes the new bottleneck | SLA + overdue alerts + inline verification at the help desk; staff it at peak hours |
| The bank refuses the teller screen | Fall back to statement import (payment confirmed later) or a hospital cashier counter. Both are already supported by the design. |
| Staff resist a new workflow | Keep the same paper copies and the same "one code" concept; pilot one area; run paper in parallel for 2 weeks; Bangla training |
| Outages during peak hours | Downtime sticker blocks + back-entry, UPS, restore drills |
| Gateway callback issues on an on-prem network | Public HTTPS reverse proxy, re-query job, reconciliation screen |
| Patient identity mix-ups | Duplicate search at registration, two identifiers on tube labels, tube-label scan confirmation |
